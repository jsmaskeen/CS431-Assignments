\subsubsection*{BufferOverflow | \texttt{python3 solution.py 1}}
{Flag} : \texttt{hello:)CS431\{ctfX\}}\\
We first decompile the given binary \texttt{vuln}, so that it is easy to read through, using \href{https://dogbolt.org/}{Decompiler Explorer}. We see that the program expects a input string, and simply, stores it in a 160 byte character buffer, without validating the length. The function call to vuln looks like:
\begin{lstlisting}[language={[x86masm]Assembler}]
vuln:
    push rbp
    mov rbp, rsp
    sub rsp, 0xa0 # 160B (the buffer size)
\end{lstlisting}
So, we need to overwrite the address at \texttt{rbp + 8}. Hence we craft our payload: of size $168 + 8$ bytes. The last 8 bytes will be the address of the function we need to call, that is \texttt{win()}, which is stored at \texttt{0x40071d} (Can be found within \texttt{gdb ./vuln}, using \texttt{p \&win}). This function opens the flag.txt and prints it to the screen. So, we simply execute: \texttt{python3 -c "import sys; sys.stdout.buffer.write(b'JASKIRAT'*21 + b'\textbackslash x1d\textbackslash x07\textbackslash x40\textbackslash x00\textbackslash x00\textbackslash x00\textbackslash x00\textbackslash x00')" | ./vuln}. Note that the function address is written as 8 bytes in little endian format. Running this results in printing out our flag.

\subsubsection*{BufferOverflowCagedBird | \texttt{python3 solution.py 2}}
{Flag} : \texttt{itsYOURcanary\{helloCTF431\}}\\ 
We first decompile the binary using \href{https://dogbolt.org/}{Decompiler Explorer}. (We can also use gdb to figure out the size of each variable, however it is easy to read decompiled binary rather than assembly. However, the addresses mentioned in the decompiled code might be wrong.) The \texttt{main()} function, first reads first four bytes of the flag, and stores it as the global canary. Then it calls the \texttt{vuln()} functions executes, it stores a copy of the value of global canary. Then it requests the user to enter an input (first it asks for the length of the input, then the input). If that input overflows, the canary is rewritten, and after that it checks, if global canary = local canary. If not then it concludes a hacking attempt. However it is easy to bypass this, as we can use brute force to guess the canary. The stack looks as follows (tracked from disassembled code):
\begin{lstlisting}
rbp+0x08   rip (return address)
rbp+0x00   saved rbp
rbp-0x04   (input loop counter)
rbp-0x0c   [padding/alignment]
rbp-0x10   local_canary (4 bytes)
rbp-0x90   buffer (128 bytes)
\end{lstlisting}
So, we will simply send a payload of size 128 (to pad the buffer) followed by 1 byte extra (this is our guess for the first byte of the canary). If for one of the 256 values of the first byte, we get ``You said something'', as output, we get to know that our guess for that byte was correct. Similarly we can find the entire 4 byte canary.

Now, we send our malicious payload, of size: 128 (buffer size) + 4 byte (known canary) + 12 bytes (padding) + 8 bytes (overwrite ebp) + 8 bytes (overwrite rip). rip is overwritten with the address of \texttt{win} function, which is figured out through gdb (using \texttt{p \&win}).
Hence, we successfully bypass the canary, and are able to execute \texttt{win()}, which prints out the flag.

\subsubsection*{Smash | \texttt{python3 solution.py 3}}
{Flag} : \texttt{cns431ctf\{0oops\_5up32\_m4210\_5m45h\_8202\}} \\ (Note: while copying the flag, underscores are not copied. Some latex issue)\\ 
We first decompile the binary using \href{https://dogbolt.org/}{Decompiler Explorer}. The vulnerability in this problem is that in \texttt{say\_hello} function, we use \texttt{strcpy}, which is unsafe. We can potentially overwrite the items on the stack, beyond the 128 byte buffer. However we do not see any function, in the decompiled code, which might leak the flag. Running \texttt{\href{https://github.com/slimm609/checksec}{checksec} ./hello} shows that we have \texttt{NX enabled}, or in other words we cannot execute any code in the stack section, by overwriting PC to some address in the stack. We are also provided with the libc shared object, which indicates that we might do a \href{https://www.ired.team/offensive-security/code-injection-process-injection/binary-exploitation/return-to-libc-ret2libc}{return-to-libc} attack, where rather than executing our own code, we try to execute functions present in the libc library such as \texttt{system()}, and \texttt{exit()}. Also we notice that the binary is compiled for a 32 bit word size environment (\texttt{i386-32-little}). We also use \href{https://docs.pwntools.com/en/stable/}{pwntools}, to get the base address of libc, however, turns out that ALSR is on, hence we need to dynamically get the base address for libc, without exiting the program. Moreover, the  binary is not PIE (position independent executable), which is a good thing, as the binary loads at the same address, so addresses in the \texttt{.text} are not randomized. We start with connecting to the server and sending our initial payload, of length 136 bytes, (128 to fill the buffer, next 4 bytes to override ebp, and next 4 bytes to overwrite eip).

To get the actual addresses of the linked libc binary, we first get the address of \texttt{printf} stored in \href{https://systemoverlord.com/2017/03/19/got-and-plt-for-pwning.html}{Global Offset Table} in the \texttt{hello} binary, then we pack it as a 4 byte unsigned integer. These are the first four bytes of our payload. Next few bytes (\texttt{plswork \%s plswork}) will exploit the format string vulnerability. Here when \texttt{printf} is called (in \texttt{say\_hello}) function, \%s will look at the first element above it's call frame in the stack, and that turns out to be the address of \texttt{printf} in GOT. 

The stack looks like this (indentation denotes child function's call frame):

\begin{lstlisting}
higher addresses
eip overwritten (main's address)
ebp (overwritten junk)
buf (128 bytes) (lower 4 bytes = printf_got)
    printf_eip
    printf_ebp
    arg: not found, sees above stack
lower addresses
\end{lstlisting}

The sting `plswork' is just to distinguish the start and end of the output written inplace of \%s. Now \%s prints until the null terminator, hence we take the first four bytes, unpack them to get the actual address of the \texttt{printf} function in the running binary. Importantly, we do not want our binary to exit, otherwise ALSR will change these addresses again, hence for the last four bytes of the payload, we overwrite eip with the address of the \texttt{main} function, which we can get from the \texttt{hello} binary (as no PIE). The remaining bytes are just padding.

With this, we can compute the offset from libc, as $\text{offset} = \text{actual\_printf} - \texttt{printf\_addr\_in\_libc.so}$. With this offset, we craft our final payload, which is 132 byte of padding (to fill buffer, and overwrite ebp), then the address of the \texttt{system} function from libc (\texttt{libc.symbols['system'] + offset}), then a random 4 byte address to serve as the return address for the system function, followed by the input to the system function, that is, `\texttt{/bin/sh\textbackslash x00}'. Executing this, gives us access to shell, and we can do \texttt{cat flag.txt} to get the flag.

If that is true for all $i$, then the program executes \texttt{cat flag.txt}, which shows us the flag.
